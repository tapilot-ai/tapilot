## First full comparison

Artifact directory: `artifacts/verification-replay/matrix-20261027-2242/`.
Ten cases, three independent repetitions each, alternating baseline/candidate
order. No automatic case or model transport retries. All 90 HTTP requests
completed successfully.

| Metric | Shipped prompt | Split prototype v1 |
| --- | ---: | ---: |
| Correct final verdict | 27/30 | 28/30 |
| False positive | 0 | 1 |
| False negative | 3 | 1 |
| Checked resolution matches fixture | n/a | 25/30 |
| HTTP requests | 30 | 60 |
| Mean sample elapsed | 7.863s | 10.848s |
| Median sample elapsed | 7.409s | 10.162s |

The amended final calculation passed 0/3 on the shipped prompt and 3/3 on the
split prototype. Both read the actual `5192÷4=1298`. The baseline still demanded
the expanded earlier expression even though the user's amendment required only
the final result.

The candidate failed two other cases:

- `read-result`, repetition 1: it classified a request to read 1298 as an
  arithmetic expression of the literal `1298`, then rejected the actual displayed
  expression. This was a false negative.
- `unevaluated-preview`, repetition 2: it routed an arithmetic requirement through
  generic visual judgment. That query accepted the editable expression and live
  preview as a committed calculation. This was a false positive, despite the
  explicit prohibition on accepting a preview. The converted query output is in
  `converted/unevaluated-preview-2-resolved/report.md`.

Other resolution mismatches added an expanded-expression requirement to ordinary
expression checks. Their negative final verdicts happened to remain correct;
that does not make the resolution correct. Generic visual resolutions were also
inspected for retained targets/restrictions; automated kind matching alone cannot
establish their complete semantic fidelity.

**Decision:** reject v1 for shipping. The improvement on the original bug does not
outweigh a newly introduced false positive. No production verifier was changed.

## Follow-up

V2 adds separate text examples for reading a value, evaluating a sequence,
explicitly requiring an expanded expression, and rejecting a live preview. The
examples use different values from the replay fixtures. It runs independently
with `--variants resolved`; it is not a new paired baseline timing comparison.
Artifact directory: `artifacts/verification-replay/matrix-v2-20261027-2254/`.
Final verdicts were correct in 30/30 samples, with zero false positives, false
negatives or HTTP errors (60 requests). Checked resolution matched in 29/30.
Mean elapsed was 10.693s, median 9.633s, on the host.

`intermediate-multiply`, repetition 1, was incorrectly routed to generic visual
judgment rather than deterministic arithmetic. Its negative verdict was correct,
but this does not establish the intended arithmetic path. Six new holdout cases
test removed versus preserved requirements, wrong values/apps, exact result
formatting and a request where reading a live preview is explicitly allowed.
The candidate is frozen before those holdouts; earlier failures remain retained.

The holdout run (`holdout-v2-20261027/`) passed all 18 final verdicts and all 18
resolution checks, across six cases repeated three times. There were 36 HTTP
requests and no HTTP errors; mean host sample time was 11.268s. Together, V2 has
48/48 correct final verdicts and 47/48 checked resolutions across 16 distinct
cases. This does not erase V1's false positive or prove general/native stability.

coordinate conversion was checked. The scorer now records both coordinate spaces;
the table uses a fresh 12-sample rerun after that repair. Regression coverage
rejects the wrong key even when the API call itself succeeds.

## Existing benchmark defect repaired

The same investigation found an independent bug in
`scripts/run-device-performance.mjs`: it expected
`shrunkShotToLogicalRatio === screenshotShrinkFactor`. The converted SDK report
actually records DPR 1 and ratio `2/3` for shrink factor `1.5`, consistent with
`DPR / factor`. A correct shrink experiment would therefore fail the old gate.
The gate now checks that ratio for **every** model screenshot, accounts for DPR,
and rejects missing or mixed scale evidence. Regression tests cover the observed
values, full-size captures, higher DPR, wrong ratios and mixed samples.
Running both predicates against the converted SDK execution returned
`oldGate:false` and `fixedGate:true` for the same recorded model task.

The installed beta deliberately fixes native screenshots to factor 1; the
existing experiment preference only takes effect in a debuggable APK. Thus no
native factor-1.5 result is claimed from this host replay or the installed beta.
