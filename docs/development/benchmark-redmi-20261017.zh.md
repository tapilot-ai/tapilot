以下顺序就是实际执行顺序。所有耗时单位为秒；“外层”和“视觉”列写作耗时 / 调用次数。设备动作是 `device.execute` RPC 次数，包含启动应用。

| 任务 | 端 / 轮次 | 验收 | 完整耗时 | 外层模型 / 次数 | 视觉 HTTP / 次数 | 剩余耗时 | 设备动作 |

| 日历 | 电脑 2 | 通过 | 40.046 | 6.268 / 1 | 22.164 / 4 | 11.614 | 3 |

八轮的外层 HTTP 重试、视觉 SDK 重试均为 0。两轮手机日历任务各在原任务内追加过一次 `phone.execute`，这属于外层 agent 的任务内规划，完整计时未中断；观察端没有重新提交任务。

外层耗时按 `model.complete` RPC 求和，包含请求编码、网络和解码。视觉耗时按模型 HTTP 的 `totalMs` 求和，包含网络及响应流。这两项都不能当作纯推理耗时。剩余耗时为完整耗时减去这两项，包含 runtime 准备、截图、界面动作、IPC、持久化和收尾。

## 独立截图核对

世界时钟四轮独立读出的城市均为伦敦、纽约。时间分别为电脑 1 的 03:29 / 10:29、手机 1 的 03:30 / 10:30、手机 2 的 03:31 / 10:31、电脑 2 的 03:36 / 10:36；纽约界面使用 12 小时制，并显示前一日“下午”。未修改城市、闹钟或日程。

两轮电脑日历最终截图同时显示“2026年11月”、选中的 15 日和“日”列，读出 **2026-11-15，星期日**。

### 手机日历第一轮：最终查询误判通过

完整耗时 89.426 秒。第一次独立查询返回 `success:false`。原任务随后追加一次手机操作，最后查询返回 `success:true`，应用状态为 `succeeded`。但最后查询所用截图已滚走年月标题和星期栏，只能看见选中的 15 日，不能独立证明年份、月份及星期。查询回答中的“2026年11月”和“日”列没有出现在该张截图中，因此人工验收否决，按失败保留。不能使用前一张截图或先前操作补足这次独立查询的证据。

### 手机日历第二轮：查询失败后未能收尾

完整耗时 275.267 秒，两次独立查询均未通过。实际截图可见 2026 年 11 月、选中的 15 日和星期列，查询却要求更明确的星期标示，构成过度保守的验证。后续未再执行手机动作，但外层模型持续调用，共 57 次，最后应用报“模型返回了空回复”，任务状态 `failed`。

采集器在 240 秒结束观察时，不能确定任务终态。随后读取同一任务的持久化状态，确认其已经失败、没有残留 worker，再恢复该任务日志及报告，取得真实 `task.wall=275267 ms`。没有重新发起任务，也没有用 240 秒替代完整耗时。

本轮仅记录这些问题，遵守暂停优化的约定，没有修改生产逻辑或验证提示来让任务通过。电脑 harness 遇到失败操作会终止，手机生产 agent 可以在原任务内继续规划，因此两端失败恢复策略也不能视为完全相同。
