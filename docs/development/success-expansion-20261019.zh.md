## 采集修正

`task.wall` 可能早于会话快照落盘。采集器现在等待同一个 task ID 的终态快照，最多 2 秒；不会启动或重放任务，也不改变任务耗时。样本记录 `taskSnapshotSettled`，避免把已完成任务的旧 running 快照误读为最终状态。

## 第二版后续发现

- 多页面读取在 240 秒采集超时后仍运行。原任务将两个互斥页面的读取合入一次操作。296.318 秒时基于真实截图点击“停止”；状态变为 `stopped`，后台 Node worker 为零。此条按未完成保留，不能因停止交互成功而计入任务成功。
- 澄清耗时 6.139 秒，正确询问应用名称且零手机操作，但状态为 `succeeded`，不符合 `waiting_user` 契约，因此严格验收失败。
- 本版截至此处为 **2/5 严格通过（40%）**，其中一条为恢复后成功。剔除连接故障单独看也仅为 2/4；不得对外宣称 95%。停止交互另有一次真实验证通过。

第三版针对这些证据补强通用规则：每次工具操作只负责一页证据，多页结果交给对话层汇总；中间步骤不能执行用户完整目标里的后续页面；即使没有手机操作，澄清也必须以 `waiting_user` 结束。另明确历史约束应在执行中遵守，截图既不能证明历史合规，也不应仅因无法展示历史而否定正确可见结果。最后一项是约束分工修正，不代表已查明跨年样本首次否定的原因。

多页面及澄清场景从此转为修复回归。第三版结果另行记录，不覆盖第二版失败。
