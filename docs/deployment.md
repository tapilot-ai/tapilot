# Android deployment workflow

`.github/workflows/release-check.yml` appears in GitHub Actions as
`Build signed deployment APK`. Pushing a `v*` tag, such as `v0.1.9`, starts it
automatically; manual dispatch remains available. It runs checks, builds and
verifies a production-signed APK, and uploads the APK and verification evidence
as an Actions artifact retained for 14 days.

## Configuration and execution

Create a `release` environment under repository Settings → Environments and
configure these secrets. Restrict the environment to release `v*` tags and
trusted branches that are allowed to run manual builds.

| Secret | Value |
| --- | --- |
| `TAPILOT_SIGNING_STORE_BASE64` | Base64-encoded production signing keystore |
| `TAPILOT_SIGNING_STORE_PASSWORD` | Keystore password |
| `TAPILOT_SIGNING_KEY_ALIAS` | Signing key alias |
| `TAPILOT_SIGNING_KEY_PASSWORD` | Signing key password |
| `TAPILOT_SIGNING_CERT_SHA256` | Signing certificate SHA-256: 64 hexadecimal characters without colons |

Create the version tag on a commit containing this workflow and push it to GitHub:

```sh
git tag v0.1.9
git push origin v0.1.9
```

Replace the example with the intended version. Creating a local tag alone does
not trigger the workflow. For manual execution, first merge the workflow into
the default branch, then select Actions → Build signed deployment APK →
Run workflow and choose the branch or tag to build. APK verification requires
`package.json` and Android `versionName` to agree.

The workflow uses Node 24, pnpm 12.4.1, Java 17, and Android SDK 35. Signed builds
share a concurrency group and do not cancel a running build. The signing file
is written to the runner's temporary directory only during the build step and
removed when that step exits.

## Artifacts and diagnostics

After a successful run, download and extract
`tapilot-signed-apk-<commit>-<attempt>`. It contains:

- `app-release.apk`: the production-signed APK.
- `SHA256SUMS`: the APK file checksum.
- `build.json`: version, source commit, workflow run ID, and signing certificate fingerprint.
- License, privacy, credits, and third-party inventories corresponding to the APK.

Run `shasum -a 256 -c SHA256SUMS` from the extracted directory to verify the APK.
The APK file checksum is distinct from the signing certificate fingerprint.
For failed runs, `deployment-reports-<commit>-<attempt>` retains available test,
Android lint, and distribution readiness reports. Reports not yet generated by
the failed run will not be present.

## Current delivery prerequisites

The workflow runs `pnpm release:review` after the full checks. This validates the
retained review receipt against the exact source lock and rebuilt Sharp manifest,
then `pnpm check:distribution` checks the generated dependency inventories before
accessing the signing key. Missing notices, changed source locks or mismatched
rebuilt binaries still fail closed; see the [materials guide](../third-party/README.md).

`pnpm release:materials` only collects evidence and writes an unapproved status.
Run `pnpm release:review` afterwards to validate the existing review bindings;
do not manually edit generated approval fields. A dependency or source change
outside those bindings needs new evidence. Final `pnpm build:release` also checks
the inventories embedded in the actual APK. Signing configuration and physical
device acceptance remain separate requirements.

This workflow delivers to GitHub Actions artifacts. It does not create a GitHub
Release, update Feishu files, or submit to an app store. Public publication requires
a specified channel and its configuration. Verify separate stable Feishu download
URLs for production and beta releases, and ensure primary and fallback downloads
have matching versions and SHA-256 checksums.
